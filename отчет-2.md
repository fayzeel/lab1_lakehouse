## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | **Рочев Егор Владимирович** |
| Вариант (запрос) | Q10 (Returned Item Reporting) |
| Масштаб `sfN` | sf1 |
| Почему выбрал такой масштаб | sf1 — это ~7,65 млн строк в Bronze (lineitem ≈ 6 млн), около 130–190 МБ в Parquet. Этого достаточно, чтобы увидеть разницу между кодеками сжатия и работу джойнов, но всё помещается в память ноутбука (MacBook Air, Docker Desktop) и пересоздаётся за секунды. Больший масштаб (sf10+) замедлил бы многократные пересоздания Bronze при тестах кодеков, не меняя выводов. |

## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO (`pgsty/silo`, форк MinIO) | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Полностью S3-совместимый API, открытый исходный код, лёгкий и локально поднимается одним контейнером; в отличие от облачного S3 бесплатный и не требует интернета. Образ `pgsty/silo` — поддерживаемый форк с актуальной консолью и образом под arm64. Бакеты `bronze`/`silver`/`gold` физически разделяют слои. |
| PostgreSQL 17 | БД, где Lakekeeper хранит метаданные каталога | Lakekeeper требует Postgres как backend; это надёжная ACID-БД с открытым кодом. Нужна только для метаданных каталога, сами данные в ней не лежат. |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Реализует открытый Iceberg REST-протокол, поэтому каталог не привязан к конкретному движку (Trino, Spark, Doris могут ходить в один и тот же каталог). Лёгкий (Rust), в отличие от Hive Metastore не тянет Hadoop/JVM-стек. Есть UI для управления warehouse. |
| Trino 476 | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Распределённый MPP SQL-движок с отличным Iceberg-коннектором (чтение, запись, DDL, time travel), стандартный ANSI SQL и встроенный коннектор `tpch` для генерации тестовых данных. Хранение и вычисления разделены, что и есть суть lakehouse. |
| DBeaver Community | SQL-клиент для интерактивной работы с Trino | Бесплатный, есть драйвер Trino из коробки, удобный просмотр схем и результатов. Это клиент, а не BI-дашборд. |

### Скрипты, которыми поднимал стек

Стек описан в `docker-compose.yml` (лежит в репозитории рядом с отчётом), конфиги каталогов Trino — в папке `catalog/` (`bronze`, `silver`, `gold`, `tpch`).

```bash
# Запуск всего стека
docker compose up -d

# Проверка, что сервисы поднялись
docker ps

# Разовые шаги после первого запуска:
# 1) миграции Lakekeeper (применяются один раз перед первым serve)
# 2) консоль MinIO http://localhost:9001 (minioadmin / minioadmin) -> создать бакеты bronze, silver, gold
# 3) UI Lakekeeper http://localhost:8181/ui -> создать warehouse bronze / silver / gold
#    (каждый привязан к своему бакету MinIO)
# 4) DBeaver: jdbc:trino://localhost:8080/bronze, user=trino
```

Что делает каждый блок compose: `lakehouse-pg` — PostgreSQL 17 с метаданными Lakekeeper (healthcheck `pg_isready`, чтобы каталог стартовал только после готовности БД); `lakehouse-minio` — объектное хранилище (порты 9000 — S3 API, 9001 — веб-консоль); `lakekeeper` — Iceberg REST Catalog на порту 8181, подключён к PostgreSQL; `trino` — SQL-движок на порту 8080, каталоги берёт из смонтированной папки `./catalog`.

## 3. Разбор запроса — какие данные нужны

Запрос Q10: топ клиентов по потерянной выручке от товаров, которые были возвращены, за квартал (Q4 1993).

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| `customer` | `c_custkey`, `c_name`, `c_acctbal`, `c_address`, `c_phone`, `c_comment`, `c_nationkey` | Джойн с `orders` по `c_custkey = o_custkey` и с `nation` по `c_nationkey`; группировка по клиенту; вывод реквизитов клиента |
| `orders` | `o_orderkey`, `o_custkey`, `o_orderdate` | Фильтр по дате: `o_orderdate >= 1993-10-01` и `< 1994-01-01` (Q4 1993); джойн с `customer` и `lineitem` по `o_orderkey` |
| `lineitem` | `l_orderkey`, `l_extendedprice`, `l_discount`, `l_returnflag` | Фильтр `l_returnflag = 'R'`; расчёт `line_revenue = l_extendedprice * (1 - l_discount)`; агрегат `SUM` |
| `nation` | `n_nationkey`, `n_name` | Джойн для получения названия страны клиента (вывод `n_name`) |

## 4. Медальон — решения по каждому слою

### Bronze (сырой)

В Bronze залиты 4 таблицы целиком (`CREATE TABLE ... AS SELECT * FROM tpch.sf1.<таблица>`), без трансформаций. Формат Parquet (дефолт Iceberg в Trino), партиционирование отсутствует. Схема: `bronze.lakehouse`.

Суммарный вес Bronze (4 таблицы) при разных кодеках: SNAPPY 190,7 МиБ / GZIP 131,4 МиБ / ZSTD 137,2 МиБ. В таблице ниже — размеры файлов по таблицам при дефолтном сжатии SNAPPY (сумма 7,8 + 35,0 + 147,2 + <1 ≈ 190 МБ совпадает с общим замером SNAPPY).

| Таблица | Колонки (что оставил) | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| `nation` | все | 25 | <1 | PARQUET | SNAPPY | нет | Крошечный справочник; партиционирование бессмысленно (один маленький файл). |
| `customer` | все | 150 000 | 7,8 | PARQUET | SNAPPY | нет | Небольшая таблица; разбиение на партиции создало бы лишние мелкие файлы. |
| `orders` | все | 1 500 000 | 35,0 | PARQUET | SNAPPY | нет | На sf1 это десятки МБ; сканирование всей таблицы быстрее, чем управление партициями. Колоночный формат Parquet читает только нужные колонки. |
| `lineitem` | все | 6 001 215 | 147,2 | PARQUET | SNAPPY | нет | Самая большая таблица (~6 млн строк), но суммарно всё ещё сотни МБ на sf1. Parquet даёт колоночное чтение и эффективное сжатие повторяющихся значений (флаги, даты). |

Итого строк в Bronze: 7 651 240. Вес по таблицам получен запросом к служебным таблицам Iceberg `"<таблица>$files"` (сумма `file_size_in_bytes`).

| Таблица | Колонки (что оставил) | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|

## 5. Тесты производительности

Запрос Q10 прогонялся при разных кодеках сжатия на Bronze. В Trino+Iceberg кодек задаётся не в `WITH`, а свойством каталога `iceberg.compression-codec` в `catalog/bronze.properties`. После каждого изменения Trino перезапускался, а таблицы Bronze пересоздавались заново.

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---|---|
| SNAPPY (дефолт, базовый замер) | 3,05 с | 190,7 | Самый большой размер. Время 3,05 с, вероятно, завышено: это был первый замер «с холодного старта» (кэши Trino/файловой системы не прогреты), поэтому напрямую сравнивать его с остальными некорректно. |
| GZIP | 1,612 с | 131,4 | Лучшее сжатие: минус ~31% к размеру относительно SNAPPY. Запрос выполнился чуть быстрее ZSTD, но разница (~0,1 с) в пределах погрешности. |
| ZSTD | 1,717 с | 137,2 | Сжатие почти как у GZIP (+~4% к размеру), при этом ZSTD обычно заметно быстрее GZIP на сжатии и распаковке. По результатам — практически равное время запроса. |

**Вывод.** Оба «тяжёлых» кодека уменьшают Bronze примерно на 28–31% по сравнению со SNAPPY. Разница GZIP/ZSTD по времени на sf1 мала и находится в пределах шума замеров, а большие различия SNAPPY vs остальные частично объясняются тем, что SNAPPY-замер был первым (холодным). Для честного сравнения нужно было бы делать несколько прогонов каждого кодека и брать медиану. Для аналитики я выбираю ZSTD: сжатие почти как у GZIP, но с лучшей скоростью работы и современным компромиссом размер/CPU. SNAPPY разумнее оставить для горячих данных с частой записью, где важна скорость кодирования.

Способы, которые не сработали (для честности отчёта): `WITH (compression = 'GZIP')`, `WITH ('write.parquet.compression-codec' = ...)` и `SET SESSION iceberg.compression_codec` — Trino отклонил их (свойство не поддерживается в `WITH` / каталог `iceberg` в моей конфигурации называется `bronze`). Рабочий вариант — `iceberg.compression-codec` в `.properties` каталога.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Lakehouse объединяет дешевизну и гибкость Data Lake (объектное хранилище S3) с транзакционностью и схемами Data Warehouse (через Iceberg). Это позволяет хранить петабайты сырых данных и делать по ним быстрые SQL-запросы без необходимости копировать данные в отдельное хранилище. Обычная БД не масштабируется до таких объёмов, а классический Data Lake не даёт ACID-гарантий и schema evolution. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Если добавить колонку `email` в таблицу Silver, Iceberg обновит только метаданные (файл `metadata.json` в каталоге), не перезаписывая старые parquet-файлы. Новые записи будут содержать новую колонку, старые — `NULL`. Это backward-compatible эволюция схемы. |
| Пример скрипта восстановления данных из снапшота (time travel) | `SELECT * FROM bronze.lakehouse.lineitem FOR VERSION AS OF <snapshot_id>;` — вернёт состояние таблицы на момент снапшота с этим id (список id: `SELECT snapshot_id, committed_at FROM bronze.lakehouse."lineitem$snapshots";`). Полезно для отката ошибочных записей или аудита. |

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| DBeaver | Бесплатный, кроссплатформенный SQL-клиент с нативной поддержкой Trino через JDBC. Позволяет интерактивно писать запросы, просматривать схемы и таблицы всех трёх слоёв медальона, экспортировать результаты. Не требует развёртывания дополнительных контейнеров (в отличие от Superset/Metabase). |

**Скрипты развертывания:** DBeaver — десктопное приложение, отдельного контейнера не требует; весь стек, к которому он подключается, поднимается через `docker-compose.yml` (см. раздел 2).

**Действия в UI:**
1. Database → New Database Connection → Trino
2. Host: `localhost`, Port: `8080`, Database: `bronze`, Username: `trino`, Password: пусто
3. Test Connection → Connected (375 мс)
4. В дереве подключений видны каталоги: `bronze`, `gold`, `silver`, `system`, `tpch`
5. SQL Editor: `SHOW CATALOGS;` → вернул 5 каталогов
6. Запросы к `bronze.lakehouse.*`, `silver.lakehouse.*`, `gold.lakehouse.*` выполняются успешно

## 7. Выводы

Медальон-архитектура удобно разделяет ответственность: Bronze хранит сырые данные без потерь, Silver содержит очищенные и объединённые данные (114 705 строк вместо 7,65 млн), Gold — готовую витрину из 20 строк для бизнеса. Lakehouse на связке MinIO + Iceberg (Lakekeeper) + Trino даёт ACID, schema evolution и time travel поверх дешёвого объектного хранилища без привязки к одному движку. Сжатие заметно влияет на объём: GZIP и ZSTD уменьшили Bronze примерно на 28–31% относительно SNAPPY, при этом время запроса не ухудшилось; я выбираю ZSTD как лучший баланс размера и скорости (оговорка: замеры единичные, SNAPPY-замер был «холодным»). Кодек в Trino+Iceberg настраивается свойством каталога `iceberg.compression-codec`, а не в `WITH`.
